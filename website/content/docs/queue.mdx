# Queue

Tako ships an in-process background job queue at `tako::queue`. It is
designed for the "fire-and-forget" workloads that usually end up
hand-rolled on top of `tokio::spawn` — send-email, dispatch-webhook,
reindex, etc. — with retry, dead-lettering, deduplication, and
delayed execution built in.

The same queue API runs on Tokio and native Compio. The `compio` feature selects
Compio worker spawning and timers; call `start()` or `spawn()` from the selected
runtime.

<RustExample path="examples/job-queue/src/main.rs" />

The builder gives you a fluent way to set worker count and retry
policy. Job handlers are registered by name with
`queue.register(name, handler)`; each handler returns `Result<(),
QueueError>`. Push jobs with `queue.push(name, payload)`,
`queue.push_delayed(name, payload, duration)`, or
`queue.push_dedup(name, payload, key)` to collapse duplicate pending
jobs by an idempotency key.

Operational helpers:

- `queue.pending_count()`, `queue.inflight_count()` — gauge-style
  metrics for dashboards.
- `queue.dead_letters()` — read the dead-letter queue. Jobs that
  exhaust their retry budget land here for manual inspection.
- `queue.spawn()` — start workers and retain a `QueueHandle` for shutdown and completion.
- `queue.shutdown(timeout)` — stop workers while ignoring the shutdown result.
- `tako::queue::cron::CronScheduler` (feature `queue-cron`) — wire
  a crontab spec into a `QueueBackend`.

## Worker lifecycle

`queue.start()` and `queue.spawn()` start the configured number of workers once.
Repeated or concurrent calls across queue clones share those workers. A stopped
queue cannot be restarted. `Queue::start()` retains its existing unit return type;
`Queue::spawn()` adds an explicit, cloneable `QueueHandle`.

Keep the handle for as long as the workers are needed. `handle.trigger()` stops
accepting jobs immediately and moves ready and delayed jobs to the dead-letter
queue. Running handlers may finish, but failed jobs are not retried after shutdown.
`handle.join().await` waits for every worker and its running job to be released.
`handle.result().await` also returns the shared completion result; multiple callers
can wait safely.

`handle.shutdown(timeout).await` triggers shutdown and returns `Ok(())` after all
workers finish. It returns `QueueRunError::Timeout` when the deadline expires and
requests cancellation of remaining workers. The timeout result is retained for
later `result()` calls. Call `join()` after a timeout to await cleanup. Cancellation
preserves unfinished jobs in the dead-letter queue, including a running handler's
payload. Handlers must yield to the runtime for cancellation to run; synchronous
blocking code cannot be interrupted.

Job handler panics are recorded as failed jobs and leave the worker available.
An unexpected worker panic produces `QueueRunError::WorkerPanicked`; a dropped
worker runtime produces `QueueRunError::Aborted`.

Dropping the last `QueueHandle` cancels its workers even if other queue clones
remain. With `start()`, dropping the last queue clone also stops the workers.
A registered handler that captures a queue clone retains that ownership; use an
explicit handle or call `shutdown()` to break that cycle. A live explicit handle
keeps workers running when application queue clones are dropped.

`queue.shutdown(timeout)` remains available and discards the result. It now waits
for workers, including their cleanup, instead of only watching the in-flight job
count. Use the handle when the application needs to distinguish clean shutdown
from a deadline expiry.

## Scheduled jobs and signals

Cron makes one enqueue attempt per scheduled occurrence. A failed push produces
an error log with the queue, scheduled time, backend error, and `policy = "drop"`.
That occurrence is dropped without retry; future occurrences still run. This
avoids resubmitting a job when a backend error leaves acceptance uncertain.

Signals are emitted for every job lifecycle event:

- `queue.job.queued`, `.started`, `.completed`, `.failed`,
  `.retrying`, `.dead_letter`

The canonical strings live under `tako::queue::signal_ids`. The queue integrates with
the in-process [signals](/docs/signals) bus, so any listener can react
to job lifecycle events.

The default `MemoryBackend` keeps everything in process. Companion
crates `tako-stores-redis` and `tako-stores-postgres` are on the
follow-up list and will implement `QueueBackend` plus the session /
rate-limit / idempotency / JWKS / CSRF stores.

See [`examples/job-queue`](https://github.com/rust-dd/tako/tree/main/examples/job-queue)
for a full end-to-end demo including retries, delayed jobs, and the
dead-letter queue.

## Capacity and retention

Queues are unbounded by default. Set limits on the builder to reject new work
before a growing backlog exhausts memory:

```rust
use tako::queue::{EnqueueError, Queue, QueueLimits};

let queue = Queue::builder()
  .limits(
    QueueLimits::new()
      .max_jobs(1_000)
      .max_payload_bytes(16 * 1024 * 1024)
      .max_dead_letters(100)
      .max_dead_letter_bytes(1024 * 1024),
  )
  .build();

match queue.try_push("send_email", &"user@example.com").await {
  Ok(id) => println!("queued {id}"),
  Err(EnqueueError::Capacity(limit)) => eprintln!("busy: {limit}"),
  Err(error) => eprintln!("enqueue failed: {error}"),
}
```

`max_jobs` counts ready, delayed, running, and retrying jobs together. A retry
keeps its reservation; workers release it when the job completes, enters the
dead-letter queue, or is cancelled. `max_payload_bytes` counts each outstanding
job's serialized JSON payload once. It also stops serialization when one payload
would exceed the entire budget. It is not a bound on total process memory:
handler-owned copies, job metadata, and caller-held snapshots are excluded.

`try_push`, `try_push_delayed`, and `try_push_dedup` return immediately when there
is no capacity, with `EnqueueError::Capacity`. Rejected work is not queued.
Pending duplicates return the existing id without using another reservation.
The existing `push` methods enforce the same limits but return capacity failures
as `QueueError::HandlerError` to preserve their error type.

Dead-letter limits are independent of the active-job budget. Retention evicts
the oldest entries first; an entry larger than the entire byte limit is discarded
without evicting smaller retained entries. `max_dead_letters(0)` disables retention. Inspect
`dead_letter_evictions()` to count discarded records and
`dead_letter_payload_bytes()` for retained payload bytes. Clearing dead letters
does not reset the eviction counter. Snapshots already held by the caller stay
alive until the caller drops them.

`outstanding_count()` and `outstanding_payload_bytes()` report active admission
usage. `pending_count()` continues to count only jobs waiting to run.

The separate `MemoryBackend` accepts the same policy through
`MemoryBackend::new().with_limits(limits)`, counting pending and reserved jobs.
Its `try_push` returns `CapacityExceeded` directly; the `QueueBackend` trait maps
that failure to `BackendError::Transport`. The older `with_max_pending` limit
counts pending jobs only. If that limit prevents a retry, `fail` returns an error
and leaves the job reserved so the consumer can retry later or dead-letter it.
